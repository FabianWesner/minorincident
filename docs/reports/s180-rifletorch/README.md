Runtime inspection (headless WebGL2 Scene Lab, 24 walking ticks and 10 attack ticks): the light-field pool's `headlamp` origin matched the held `torch-lens` world position in both HIGH and LOW walking samples: (1.29385, 0.78960, 0.17333). Its horizontal offset (2.63201, 0) was parallel to the lens node's +X axis (0.63964, 0). LOW firing sample: lens and pool origin both (0.52214, 0.89577, 0.20818), with pool offset (2.98588, 0.00679) parallel to the node axis (0.65014, 0.00148). These samples establish the submitted footprint's origin and horizontal heading for those poses only; reload, idle, other facings and WebGPU torch behavior remain unverified.

Additional headless HIGH WebGPU runtime inspection used the actual `WebGPUBackend`: 20 samples covering four initial yaws (0°, 90°, 180°, 270°) and idle, walk, aim command, attack command and an active reload timer. In each sample the torch and holder were visible, the submitted pool origin equalled the lens world position within 0.00001 m, and its horizontal offset was parallel and forward to the lens +X axis. The reload fixture sets an empty magazine and `reloadUntil` directly; it does not verify a distinct reload animation. The aim-command samples retained the idle pose, so they do not establish a raised aim pose. Walking and attack commands can change the final heading from the initial yaw. The run reported no browser errors.

Raised aim follow-up: Scene Lab's ordinary aim command sets a pointer direction without `pointerTarget`, so it did not raise the weapon in the earlier probe. A temporary probe preserved that command's target direction and changed the input source to keyboard; the game's `gunReady.ticks` reached 6 in all four initial yaw cases. On HIGH WebGPU, each raised sample kept the submitted light origin within 0.00001 m of the lens and its horizontal direction parallel and forward to the lens axis. All four aimed at the same target, so they converge on the same final heading; this is not a four-direction raised-aim sweep.
